This page explains where Speccy spends model tokens, how the estimate and the monthly budget work, and how to lower the cost.

## What costs tokens

Lint calls no model. It runs on every save and costs nothing. Every other step calls the model of a role, and each call counts its input and output tokens.

| Work | Role | Calls |
|---|---|---|
| Rubric stage | reviewer | One call per batch of 8 whole-doc checks. One call per batch of 8 checks for each section that checks name. A check with section scope adds one batch for each section. |
| Grounding stage | reviewer | One call per section of 12 words or more to find the claims. Then calls that label the claims, with web search when the backend has it. |
| Divergence stage | reviewer, readers, judge | One call to write the build questions, when the doc has none yet or has new sections. One call per reader per batch of 10 questions that the readers answer again. About one judge call per question, when 2 or more readers answer. |
| Coherence stage | reviewer | One call per linked doc that the contradiction check reads. |
| A suggested fix, an AI answer in a thread, a diff summary | writer | One call each. |
| A verification run | reviewer, judge | The reviewer maps trace IDs to the code. The judge reads each cited target. A contradiction gets a second judgement from the model of another role. |
| **Test** on a backend | the tested backend | One short call. |

After an HTTP 429 or 5xx answer, Speccy retries the call. When the answer has a `retry-after` header, Speccy waits that long first. Otherwise it waits longer after each try, up to 30 seconds. A call in a review run retries while the run has time left. A call outside a run retries up to 6 times. Speccy asks again once when an answer is not valid JSON for the step. Every attempt counts.

An agent CLI that reports no token counts gets an estimate: the length of the prompt and the answer, divided by 4.

## The cache

Speccy caches the answer of each step. A step with the same input, profile version, prompt version and model reads the answer from the cache, and it costs nothing. An unchanged section therefore costs nothing on the next review. Its AI findings stay as carried findings.

After an edit to one section, a full review calls a model for these steps only:

- The rubric checks that name that section, and the whole-doc checks. A whole-doc check reads the whole doc, so any edit sends it to the model again.
- The grounding of that section.
- The build questions that cite that section, and the questions that were a gap or a divergence. A question that the readers agreed on, with unchanged cited text, keeps its answers.

A rubric check that names a `section` in the profile therefore costs less than a whole-doc check. [Change a profile](/how-to/change-a-profile/#add-a-rubric-check) shows the key.

The cache key holds the backend kind and the model. When you change the model of a role, the next review calls that model for every step again.

## The estimate before a review

A full review starts from the next action **Check this doc**, or from **More → Run a review** in the control row. Both open the **Run a full review** dialog before any call. The dialog shows:

- **Model calls**: the calls that the cache cannot answer.
- **Steps from the cache**: the steps with a cached answer.
- **Tokens (estimate)**: the input and output tokens together, at about 4 characters per token.
- **Cost (estimate)**: the tokens times the prices of the roles, or `No prices set`.

The estimate needs a model for the reviewer, the readers and the judge. When a role has none, the dialog says so and links to **Admin**.

To get a cost in dollars, set the prices of each role in **Admin → Models → Roles**. The two fields, `$ in / M` and `$ out / M`, take the price per million input tokens and per million output tokens. Speccy uses them for the estimate and the run report only. For an OpenRouter model, Speccy fills in both fields from OpenRouter's model list when you pick the model. For each other backend, you type the prices.

The estimate is a rough count. It counts every reader and judge call, although the cache can answer some of them. It leaves out rubric checks with section scope.

After the run, the verdict shows the real count: `Full review of v3: 48,210 tokens, about $0.41, 12 steps from the cache.`

## The monthly budget

The budget caps the tokens of one workspace in one calendar month, in UTC. Every model call counts against it: reviews, verification runs, writer calls and **Test**. A cached step does not count.

Hosted mode has one limit for each queue:

| Limit | Queue | What counts against it |
|---|---|---|
| **Reviews a person waits for** | `interactive` | The reviews from the app, the CLI and MCP, the AI answers in threads, the verification runs, and **Test**. |
| **Pull request reviews of the GitHub App** | `pr` | The pull request reviews of the GitHub App. |

A spent limit stops its own queue only. A flood of pull requests cannot stop the reviews of people, and the reviews of people cannot stop the pull request checks. Local mode shows only **Reviews a person waits for**.

### Set the budget

1. Open **Admin → Models**.
2. Under **Monthly token budget**, type the limit of each queue in tokens.
3. Select **Save**.

An empty field means no limit. The section shows the tokens used this month, and a bar when a limit exists. The bar turns red at 90%.

At 80% of a limit, Speccy posts one message to the workspace channel, when the workspace has one. [Run hosted mode](/how-to/run-hosted-mode/#send-notifications-to-a-channel) sets the channel.

An upgrade from a release with one limit copies that limit to both queues.

### See where the tokens went

In hosted mode, the section also shows the spend of this month in one table. Each row is one queue, one person and one repo, with the tokens and the cost. The person of a pull request review is **GitHub App**. A review with no repo shows `—` in the repo column.

The limit carries into the next month. The count of used tokens starts at 0 on the first day of each month.

A limit of 0 stops every model call.

### At the limit

Speccy checks the budget before each model call. When the used tokens reach the limit, the call fails with this message:

```text
Review stopped: the monthly token budget is spent. An admin can raise it in Admin → Models.
```

When the `pr` limit is spent, the review of the GitHub App stops with this message:

```text
Review stopped: the monthly token budget for pull request reviews is spent. An admin can raise it in Admin → Models.
```

In blocking mode, the check of the pull request then fails. A review that cannot finish fails, because lint alone can show Build Ready while a material gap is open. The reviews of people go on.

- A review run fails at the stage that made the call, and gives no verdict. The control row shows **The last review failed**, and the verdict details show the cause.
- Lint still runs on every save.
- **Test**, a suggested fix and an AI answer in a thread fail with the same message.

Speccy checks before each call, not during it. Calls that already started finish and count, so the used tokens can pass the limit by the size of those calls. **Model calls at a time** in **Admin → Workspace settings** sets how many calls one review runs at once. The default is 8.

To go on, raise the limit or clear the field, and select **Save**. Then run the review again.

### The budget and CI

Each store has its own budget. `speccy review` and `speccy action` use the budget of the store they open:

- With `.speccy/state/` in the folder, they share the budget of local mode.
- With `SPECCY_STATE_DIR`, they use the budget in that folder.
- `speccy review --server` runs the review on the server, so it spends the server's `interactive` budget.
- With no store, they use a temporary one with no limit.

The GitHub Action sets no budget. The GitHub App of a hosted Speccy spends the `pr` budget.

## Spend less

- **Review after the doc settles.** Lint runs on every save for free. Run a full review when a draft is ready for its verdict.
- **Let the cache work.** Change the sections that need it, and leave the rest alone. Keep the same model on the reviewer role between reviews.
- **Use a cheaper model for the readers.** A reader answers build questions from the doc alone. Each role takes its own backend and model. The judge also decides the outcomes of a verification run, so keep a strong model there.
- **Mix model families for the readers.** Diversity costs nothing extra. When fewer than 2 different models answer as readers, the run report says `Low reader diversity`. The note never blocks the verdict.
- **Ask fewer build questions, with fewer readers.** In the profile, `divergence.readers` takes 1 to 3, and `divergence.questions.max` caps the questions. With one reader, the divergence test calls no judge, and it can find gaps but no divergence. [Change a profile](/how-to/change-a-profile/) shows how.
- **Choose the stages in the CLI.** `speccy review --stages lint,rubric` runs lint and the rubric only. The run judges only those stages, and the run report says so. The findings of the other stages stay from the last review that ran them.
- **Run lint only.** `speccy review --stages lint` calls no model. In the GitHub Action, leave out the `models` input, and only lint runs.

```sh
speccy review docs/specs --stages lint,rubric,coherence
```

The app always runs every stage in a full review.
